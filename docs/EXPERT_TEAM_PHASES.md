## 已实现的能力

### 1. 六个角色，职责边界用数据声明

| 角色 | 关注维度 | 明确不看 | 默认权重 |
|---|---|---|---|
| 结构师 | 情节结构、节奏、设定一致性 | 文字、对白 | 1.0 |
| 人物塑造师 | 人物、设定一致性 | 文字、节奏、对白 | 1.0 |
| 对白作家 | 对白、人物 | 结构、节奏、文字 | 0.9 |
| 文字编辑 | 文字、对白 | 结构、节奏、人物、类型 | 0.9 |
| 读者代表 | 读者体感、节奏 | 文字、结构、设定、对白 | 0.8 |
| 类型守门人 | 类型惯例、结构、节奏 | 文字、对白、人物 | 1.0 |

**边界是数据不是 prompt**——`focus` / `ignore` 两个数组在代码里声明，裁决阶段直接拿它做越界降权，可验证。prompt 里写「你别管别人管的事」是管不住的。

读者代表权重最低（0.8）并带 `intuitive: true` 标记：它做的是**体感判断**而非技术诊断，与其他角色不同量纲，冲突时该让位。

### 2. 五级裁决规则（按序执行，先命中先生效）

| # | 规则 | 触发条件 |
|---|---|---|
| 1 | 硬约束优先 | 一方 `block` 而另一方不是 |
| 2 | 严重度优先 | 严重度差 ≥2 级且最高级唯一 |
| 3 | 角色权重 | 严重度断层但最高级有多方，按权重 |
| 4 | 类型惯例优先 | 同权重且该维度属类型守门人 focus |
| 5 | **弃权交作者** | 权重并列且无类型惯例兜底 |

**规则 5 是一等公民**：`defer` 表示「专家团不假装总能给出答案」。真冲突时把选择权交还作者，比硬凑一个结论有价值。UI 上它必须显眼，且置信度恒为 0.5（标记「无共识」），不伪装成高置信。

### 3. 越界降权

某角色对它 `ignore` 的维度提意见 → 标记 `crossBoundary` 且权重 ×0.3。**不删除**——一个文字编辑跑去说「节奏有问题」是越界，但这个观察仍有参考价值。

权重配置覆盖优先于越界惩罚：用户显式配了 `reader: 2.0` 就是 2.0，不该再被打折。

### 4. 冲突信息完整保留

裁决结果里 `opinions` 保留**全部**参与意见（含被否决的），因为「哪方被否决了、为什么」本身是用户需要的信息。`conflict` 字段记录分歧描述、参与方、命中的规则。

### 5. 润色前后对照

`compareReports()` 逐维度给出 `improved` / `regressed` / `same`。这是「润色是否真的变好了」的唯一客观依据——规则引擎会全量应用所有规则而不问效果。

## 三项约束怎么落地的

### 可开关

```ts
registerExpertTool(registry, config, deps)
// ↓
if (!config.enabled) return false;  // 不注册
```

配置 `enabled: false`（默认）时，工具**根本不进注册表**——不是「注册了但不用」。Agent 的 `tools` 列表里没有它，模型看不到，原流程**性能零影响**。

### 按需加载

- 角色定义是**静态数据**，不构造 prompt、不发 LLM 请求
- 只有 `activateRoles()` 实际激活时才产生开销
- 三个阶段默认规模不同：`outline` 2 个、`post-polish` 2 个、`chapter` 6 个

若每阶段都 6 个全开，专家团会成为性能负担，用户也会因「每次都要等 6 个人」而弃用。

### 不影响原流程

1. 专家团是**独立工具**，不在 Agent 主循环的必经路径上——循环、工具注册、checkpoint 体系逻辑未改
2. 工具标为 `idempotent: true` → 循环检测判据 A 豁免，不会把「连续评审 3 次」误判为循环
3. 预算独立（`config.budget`），**不与 Agent 循环共享池子**——专家评审超支不会把 Agent 带停
4. `danger: Precise`（★1）——只读工具，不进 checkpoint，不触发快照

## 数据持久化

迁移 v5 建两张表：

| 表 | 用途 |
|---|---|
| `expert_reviews` | 每次评审一条：阶段、激活角色、裁决结果、token/成本/耗时、状态 |
| `expert_opinions` | 每条意见独立成行：角色、维度、严重度、**生效权重**、**是否越界**、**是否被采纳** |

**为什么拆两张**：意见独立存表后可回答「哪个角色最常提哪类问题」「什么意见最终被采纳」——`dimensionStats()` 已实现这个聚合，为后续权重自动调优提供数据基础。

`adopted` 字段映射：`accept`→1、`reject`→0、**`defer`→NULL**（待作者裁决）。这个 NULL 本身就是数据——它标出了「专家团解决不了、只能作者拍板」的维度分布。

## 怎么用

### 接入（三道门全过才注册）

```ts
import { registerExpertTool } from './src/main/expert/tool';
import { DEFAULT_EXPERT_CONFIG } from '@shared/types/expert';

const config = { ...DEFAULT_EXPERT_CONFIG, enabled: true }; // ① 总开关

registerExpertTool(registry, config, {
  getChapterBody: (id) => chapterRepo.bodyOf(id),
  getChapterTitle: (id) => chapterRepo.titleOf(id),
  reviewer: {                                              // ② LLM 依赖
    llm,                    // LlmClient 实例
    provider,               // LlmProvider（用于成本换算）
    config,
    getChapterBody: (id) => chapterRepo.bodyOf(id),
  },
});                                                          // 返回 true = 已注册
```

**三道门**（任一不满足则**不注册**，Agent 完全看不到该工具）：
1. `config.enabled === true`
2. 提供了 `reviewer` 依赖（没有 LLM 就注册了也必然失败）
3. 角色列表非空

### 阶段二新增的编排能力

| 能力 | 实现 | 验证 |
|---|---|---|
| **部分失败不拖垮整团** | 逐专家 try/catch，失败的记入 `failed[]`，其余照常返回 | 6 专家挂 1 个 → 其余意见完整返回 |
| **并发上限 3** | 3 个 worker 抢队列 | 峰值并发 ≤3，避免打满 provider 触发限流 |
| **预算闸** | token / 成本双闸，超限停止发起新调用并标 `budgetTruncated` | 达到上限后调用次数 < 角色数 |
| **本地模型不误截断** | `pricing === 0` 时跳过成本闸，只看 token | 3 角色 × 450 token 不被截断 |
| **宽松 JSON 解析** | 兼容 ```json 围栏、JSON 前有解释文字 | 5 种格式全部解析成功 |
| **逐项点名校验** | Zod safeParse 逐条校验，非法条目丢弃但保留合法条目 | 部分不合法 → 保留合法的 |
| **evidence 强制非空** | 拒绝空 evidence（必须引用原文，不许编造） | 空 evidence → 该专家标记失败 |
| **整体超时** | `AbortController` + `timeoutMs` | 防止评审无限跑 |

### 降级信息的传达

`describeFailures()` 把缺席专家转成人话，**并明确告知意见不完整**：

```
⚠ 以下专家未完成评审：人物塑造师（auth: API Key 无效）。意见不完整，请勿据此下完整结论。
```

这段话会进 `narration`，**模型能读到**——否则模型会以为意见是完整的而照单全改。这是「失败不隐藏」原则在专家团里的落点。

## 实现过程中修的三个真 bug

值得记下来，因为都是**写测试时暴露的**：

### 阶段一
1. **权重覆盖被越界惩罚重复打折** — 用户配了 `reader: 2.0`，若 reader 恰好越界会变成 0.6。改为「权重覆盖优先，越界惩罚只作用于未覆盖的基础权重」。
2. **defer 的置信度算错** — 原本 `totalWeight > 0 ? 0.5 : 0` 里 `totalWeight > 0` 恒真，导致输出 0.789 假装有共识。改为 defer 恒为 0.5。

### 阶段二
3. **预算闸完全失效（最严重）** — `usage` 对象**从未被累加**，`budgetExceeded()` 永远读到 0，等于没有闸门。这个 bug 在静态阅读时完全看不出来，是「达到 token 上限后停止调用」这条测试抓出来的。
   - 同时暴露第二个问题：并发 worker 各自检查预算会**同时通过初始检查**（竞态）。修法是把检查与累加都放在 worker 内的串行位置。
   - **教训**：任何「预算/配额/限流」逻辑，必须有测试证明它真的会拦；光看代码觉得写了不等于生效。

### 另外 4 处是我的测试写错（不是代码错）
用同角色提矛盾建议（现实中不会发生，且 evidence 相同时被 Jaccard 去重误合并）、给 defer 用例加了 `block`（撞上更高优先级的规则 1）、造「权重并列」时误以为 reader(0.8) 与 dialogue(0.9) 并列。**都是先判「谁的错」再改的。**

排查手法：写临时探针打印去重后还剩几条、各自权重多少，比反复猜快得多。
