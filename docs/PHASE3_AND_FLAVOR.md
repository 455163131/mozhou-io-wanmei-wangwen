## 三、AI 味检测板块

### 3.1 定位：写作体检，不是 AI 判决

**这是朱雀调研得出的最重要结论，也是本板块的产品原则。**

朱雀是**二分类器**——输出「AI 生成概率%」，不解释原因。它在中文上有公开的误判实证（老舍《林海》被判 99.9% AI），且**网文本身就套路化**（打脸、金手指、章末钩子），天然长得像统计平均，被误判风险显著更高。

所以墨舟不报「你有 87% 是 AI」，而是报**可核对的事实**：

> 第 3 段句长集中在 22–26 字，节奏偏平；「随着…的发展」出现 3 次；逗号/句号比 4.2（偏高，长句压读）

这段免责声明已内置在 `FLAVOR_DISCLAIMER`，面板底部常驻显示。

### 3.2 十个检测维度

分值方向：**0 = 人写，100 = AI 生成**（与朱雀的「AI 生成概率」同向）。

| 维度 | 可计算特征 | 人写参考 | AI 参考 | 权重 |
|---|---|---|---|---:|
| `sentence-rhythm` 句子节奏 | 句长变异系数 | >0.6 | 0.25–0.4 | 0.12 |
| `paragraph-rhythm` 段落节奏 | 段长变异系数 | >0.75 | <0.3 | 0.08 |
| `lexical-diversity` 用字多样性 | 单字 TTR | 0.12–0.18 | 0.06–0.10 | 0.10 |
| `phrase-repetition` 短语重复 | 三字片段重复率 | <0.1 | >0.25 | 0.14 |
| `opening-pattern` 句首模式 | 同两字开头占比 | <0.08 | >0.15 | 0.08 |
| `template-connector` 模板连接词 | 命中数/千字 | <0.5 | >1.5 | 0.15 |
| `marker-density` AI 味标志词 | 命中数/千字 | <1 | >3 | 0.18 |
| `punctuation-pattern` 标点模式 | **逗号/句号比** + 破折号省略号密度 | 1.2–2.5 | >2.5 | 0.05 |
| `dialog-ratio` 对白占比 | 含对白段落比例 | >0.35 | <0.05 | 0.05 |
| `parallel-structure` 排比工整度 | 对仗结构/百句 | <1 | >5 | 0.05 |

**权重设计依据**：越「作者能直接动手改」的维度权重越高。标志词与模板连接词权重最高（改动动作明确）；排比工整度最低（网文里适度对仗是正常文风，误判率高）。

**取自朱雀调研的三处新增**：
1. **逗号/句号比**（P0-2）——网文「长句压读」硬伤，人类网文多在 1.2–2.5，AI 常见 3–6
2. **副词+动词结构**（P1）——「缓缓说道」「淡淡一笑」，网文命中率高、误报可控
3. **成对结构独立处理**——「不仅…而且」，「不仅」单独出现不算问题（见下方踩坑记录）

### 3.3 实测分离度

| 样本 | 指数 | 等级 | 命中数 | 问题段落 |
|---|---:|---|---:|---:|
| 人写（对白密集的市井场景） | **4** | 干净 | 0 | 0/14 |
| AI 腔（套话密集） | **53** | 可疑 | 20 | 13/14 |

**分离度 49 分，人写文本零误报命中。**

### 3.4 两条改写路径（局部重写）

| 路径 | 入口 | 特点 | 适用 |
|---|---|---|---|
| **auto-rule** | 「一键自动改写」 | 本地规则，**不调 LLM**，可离线、零成本 | 已知怎么改的问题（模板连接词、套话） |
| **agent** | 「交给主 Agent 重写」 | 构造 goal 交给 `AgentHost`，走 Agent 循环 | 需理解上下文才能改好的（人物语气、情节衔接） |

**共同硬约束：只做局部重写，不做整篇重写。** 整篇重写会丢掉作者的风格指纹，而风格正是这个工具要保护的东西。

实测（AI 腔样本）：

```
改前 53 → 改后 36（↓17）
10 处本地改动，9 处交给 Agent
改写结果：「他瞳孔骤然紧缩。」「这一切都是那么不易察觉。」——通顺
```

**前后分对比用真实重跑**，不是估算。`diffReports()` 会如实报出**变差的维度**——局部改写真可能按下葫芦浮起瓢，只报好消息的对比是自欺。

### 3.5 配置参数

```ts
interface FlavorConfig {
  enabled: boolean;                    // 总开关
  dimensions: Record<FlavorDimension, boolean>;  // 10 个维度独立开关
  weights: Partial<Record<FlavorDimension, number>>;  // 权重覆盖
  thresholds: {                        // 五级判定阈值
    clean: 25; mild: 40; suspicious: 55; heavy: 70;
  };
  minChars: 200;                       // 最小样本量（低于此不出总评）
  includeExcerpts: boolean;            // 是否回传原文片段（大文本可关以省传输）
  maxHits: number;                     // 单章最多返回多少命中（防压垮 UI）
}
```

**`minChars` 是防冤枉作者的关键**：短文本的所有多样性指标天然偏低（空文档会得 7 项 risk），硬判会冤枉人。低于阈值直接标记 `sufficient=false` 并拒绝出总评。

### 3.6 异常与降级

| 情况 | 处理 |
|---|---|
| 非字符串入参（编辑器清空 / 脏数据） | 转空串，不抛错 |
| 文本低于 `minChars` | `sufficient=false` + 说明原因，指数记 0 |
| 维度全关（权重和为 0） | 总评记 0，不崩 |
| 命中数超 `maxHits` | 按严重度降序截断 |
| 偏移越界（脏数据） | 跳过该处，不破坏文本 |
| 本地规则改动会产生病句 | **安全护栏拦下**，转交 Agent 路径 |
| Agent 不可用（未配模型） | 明确报错，不静默降级 |

## 四、专家团阶段三

### 4.1 交付内容

| 项 | 说明 |
|---|---|
| **IPC 通道** | `expert:review` / `history` / `opinions` / `decide` / `config` / `configure` / `roles` |
| **preload API** | `window.mz.expert.*`（白名单，不暴露 ipcRenderer） |
| **面板** | 阶段选择 / 角色多选 / 结论列表 / **冲突可视化** / **作者裁决入口** |
| **持久化接线** | 每次评审写入 v5 两张表（`status='partial'` 记录部分失败） |
| **作者裁决** | `decide()` 把 defer 项的决定写回 `adopted` 字段留痕 |

### 4.2 面板的三个设计要点

1. **角色多选可见化**——勾选几个就跑几个，未勾选的「不参与、不产生费用」直接写在界面上。这是「按需加载」承诺的可见化。
2. **冲突视觉最突出**——冲突卡片左侧加粗警示条，双方意见并列展示，标出裁决依据（命中哪条规则）。冲突是专家团最有价值的信息，不能埋在列表里。
3. **defer 项有明确拍板入口**——「采纳建议」/「保持原样」两个按钮，决定写回数据库留痕（后续权重调优的标签）。

### 4.3 降级处理

| 情况 | 处理 |
|---|---|
| 模型未配置 | 明确报错「专家团评审需要可用的模型，请在设置中配置 provider 后重试」 |
| 部分专家失败 | `status='partial'` 落库 + 面板顶部醒目提示「意见不完整」+ 列出缺席者与原因 |
| 无章节可评 | 明确提示，不静默返回空 |
| 角色列表为空 | 抛 `E_INVALID_ARGS` 并列出可用角色 |

## 五、如何运行与测试

### 5.1 运行

```bash
cd MozhouAgent
npm install
npm run dev          # 启动应用
```

打开项目 → 右侧 tab 切到 **「AI 味」** 或 **「专家团」**。

### 5.2 板块用法

**AI 味检测**：
1. 点「开始检测」→ 出总指数 + 10 维度得分 + 问题段落 + 命中片段（每处带原因与改法）
2. 点问题段落 chip 可**限定改写范围**（只改这一段）
3. 「一键自动改写（本地规则）」→ 立即出前后分对比
4. 「交给主 Agent 重写」→ 派给 Agent 循环处理需理解上下文的片段

**专家团**：
1. 选阶段（大纲 / 章节 / 润色后复检）
2. 勾选激活专家（默认按阶段给不同组合）
3. 点「开始评审」→ 出结论列表，冲突项高亮
4. defer 项点「采纳建议」/「保持原样」拍板

## 六、实现中修的四个真 bug（都由测试抓出）

1. **段落节奏误判人写文本（92 分）** —— 网文对白场景大量用一两句话一段，段落长度**天然高度整齐**，用一般散文基线去判会冤枉人。这是朱雀调研预警的头号风险，实测真的踩到了。改为：段落中位 <120 字时该维度**不参与判定**。
2. **注释说「不计为问题」但分数仍给 92** —— 分数与结论矛盾。这是坏味道：不能让一个字段说有问题、另一个说没问题。
3. **`嘴角勾起` → `笑了一下` 产生病句** —— 「他嘴角勾起一抹苦笑」变成「他笑了一下一抹苦笑」。**我违反了自己写的原则**（本地规则瞎改比不改更糟）。已删掉这类 replace 规则，改由 Agent 处理。
4. **「不仅」被当连接词删掉** —— 「不仅仅是身体的疲惫」变成「是身体的疲惫」。裸的「不仅」在正常中文里太常见，已从词表移除，改为只检测「不仅…而且」成对结构。

**另有 3 处是我的测试写错**（样本长度不足 200 字触发保护、用 `require` 在 ESM 里、断言写反），都是先判「谁的错」再改的。

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 阈值是通用基线 | 未在本项目真实网文语料上校准（阶段四待做）。报告里的「人写参考值」来自通用中文语料，网文场景可能要调 |
| 无困惑度类指标 | 朱雀的核心指标依赖语言模型逐 token 打分，**本地零模型算不了**，故本板块只做统计与风格特征 |
| 简繁未归一 | 繁体文本会让部分词表失配（词表是简体） |
| 专家团评审成本 | 六位专家 = 六次 LLM 调用。已有独立预算闸与并发上限 3，但用户仍需注意 |
| 章节选择 | 专家团面板目前取前 5 章，未接入选中章节的交互 |

## 八、下一步建议

1. **阈值校准（阶段四）**——用你的真实稿子跑一遍分布，取 p05/p95 做基线。现在用的是通用基线，这是最影响准确度的一项。
2. **接入选中章节**——让专家团与 AI 味检测都支持「只处理当前选中章节」。
3. **章末钩子强度**——网文独有维度，竞品几乎没有，可作为差异化点。
